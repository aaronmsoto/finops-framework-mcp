Is Prompt Caching Paying Off?

Prompt caching is one of the biggest levers on an AI bill, and one of the easiest to get wrong. This page walks the chain an agent follows with all three servers: the FinOps Framework names the KPI → the Tokenomics Foundation supplies its formula and the calculation → FOCUS™ shows where the token data lives in billing exports today and in 1.5.

finops-framework-mcp · the KPI tokenomics-overview-mcp · the formula and the math finops-focus-mcp · the billing columns
1

The FinOps Framework names the KPI official

Searching the framework for “cache hit rate” finds one KPI in its library:

“Measures the percentage of tokens used from cache. Cached tokens are significantly cheaper. A low cache hit rate signals an optimization opportunity for FinOps Practitioner and Engineering Personas.”

The record has no formula, no data sources and is not featured on any capability page yet. It says what to watch, not how to compute it. That is the gap the next server fills.

framework · search_framework {query: "cache hit rate"} · get_kpis {slug: "cache-hit-rate"}

2

Tokenomics supplies the published formula quoted

Cache hit rate = cache read / (cache read + cache write + uncached input)
“One number, built from the three buckets above, bounded between 0 and 100%. Bounded is what makes it composable: you can average it, roll it up across teams and workloads, and put it on the same slide as any other percentage.”

What good looks like, per the cache explainer: “climb toward your workload's ceiling … A live chat can never reach 100% because the conversation grows, so track the trend against the structural ceiling, not toward perfection.”

A hit rate alone can't tell you whether caching saves money, because cache writes usually cost more than plain input. The explainer pairs it with a second metric:

Cache cost efficiency = 1 − actual prompt cost / uncached equivalent cost
uncached equivalent cost = (cache read + cache write + uncached input) × base input price

Source status: Release Candidate 1 (2026-09-22) · “AI Tokenomics Prompt Cache Explainer”.

tokenomics · get_metric {metric: "cache-hit-rate"} · list_metrics {}

3

Run the numbers on two workloads

Both runs use 1 million input tokens at a $3 per million base input price, a 0.1× cache-read rate and a 1.25× cache-write rate. Those rates match the provider snapshot the server also serves (Anthropic: write 1.25× base with a 5-minute TTL, read 0.1× base). Only the mix of tokens differs.

Workload A · stable prefix

70.8%

cache cost efficiency · hit rate 80.0%

read 800,000 · write 50,000 · uncached 150,000 uncached equivalent cost = $3.00 actual prompt cost = $0.8775

Workload B · prefix keeps changing

−1.0%

cache cost efficiency · hit rate 10.0%

read 100,000 · write 400,000 · uncached 500,000 uncached equivalent cost = $3.00 actual prompt cost = $3.03

The server interprets each result. For workload B:

“Cache hit rate 10.0%; cache cost efficiency -1.0% — negative: caching is costing more than it saves (writes not read back enough). Cache writes (400000) exceed cache reads (100000): per the cache explainer, a write “pays back only if that entry is read again, ideally many times.”

The tool computes only what you pass in: output tokens, batch or committed-use discounts and contracted rates sit outside this input-side ratio, and it says so in every response.

4

Find the lever, and what breaks it

Caching is the primary lever at L3, the inference stack:

“Prefix, KV, and semantic cache — Primary lever for L3 Inference stack (key metric: Cache hit rate, time to first token, throughput). Yes, toward T(1) and T(log n).”

For workload B, the assess_prompt_caching prompt gives the agent its checklist: put stable content first, growing content next and per-request content last; then flag what silently breaks the prefix: “timestamps, re-serialized JSON, tool list churn, model switches, router spreading load.” The last two connect caching to the model-routing demo: a router that switches a long session to another model re-reads the whole prompt uncached.

tokenomics · get_lever {lever: "l3-prefix-kv-and-semantic-cache"} · prompts/get assess_prompt_caching {workload: "support chatbot with a 6k-token system prompt"}

5

Where the token data lives in FOCUS

To track this KPI from billing data rather than provider dashboards, you need cache reads, writes and uncached input labelled per price. In the ratified FOCUS 1.2 that information can only travel in a general-purpose column:

Column (FOCUS 1.2)TypeFeature levelData type
SkuPriceDetailsDimensionConditionalJSON (key-value), introduced in 1.1

FOCUS 1.5 adds standard properties for exactly this, in the working draft and due for ratification on 3 Dec 2026:

“TokenCacheAction takes "Uncached", "Read", "Write", or "Other" on prices that meter only tokens consumed from a request. TokenDirection takes "Input" or "Output" on prices that meter tokens in one direction.” “They are the first FOCUS-defined SKU Price Details properties with a fixed set of allowed values.”

The tokenomics server states that link with its evidence and returns focus://spec/1.2/columns/skupricedetails for the FOCUS server to read. The draft property names have no URI, because no ratified FOCUS release contains them yet.

focus · get_column {column: "SkuPriceDetails"} · tokenomics · get_focus_ai_tracker {identifier: "TokenCacheAction"} · get_crosslinks {entity_type: "focus-item", slug: "fr-2099"}

Close the loop UNOFFICIAL

No Foundation page links the framework's KPI to the tokenomics metric, so the default surface doesn't either. With FINOPS_MCP_EXPERIMENTAL=1, the server's curated crosswalk does, and labels itself:

_UNOFFICIAL: curated crosswalk entries are this server's own mappings; no Tokenomics
Foundation page states them._

- metric **cache-hit-rate** → framework kpi **cache-hit-rate**
  (`finops://framework/kpis/cache-hit-rate`): Same name. The framework KPI describes
  the percentage of tokens used from cache without a formula; the Tokenomics Foundation
  formula supplies the denominator (cache read + cache write + uncached input).
- metric **cache-hit-rate** → framework capability **usage-optimization**
  (`finops://framework/capabilities/usage-optimization`): Raising cache hit rate removes
  recomputed input tokens, which is consumption reduction rather than a rate change.

tokenomics (FINOPS_MCP_EXPERIMENTAL=1) · get_crosswalk {entity_type: "metric", slug: "cache-hit-rate"}

What the agent can now tell you

The KPI to report (FinOps Framework), how to compute it and whether caching actually saves money (Tokenomics: 70.8% saved on workload A, a 1.0% loss on workload B), the lever and the layout rules to fix B, and where the three token buckets will appear in your FOCUS data: in SkuPriceDetails today, as standard properties once FOCUS 1.5 is ratified. Each part comes from a different server, and each is cited.
