Tokenomics Overview MCP

approved in question round · 2026-09-25  ·  spec: .agents/specs/tokenomics-overview-mcp.md  ·  roadmap: .agents/roadmap.md

Summary. A third MCP server, tokenomics-overview-mcp, gives agents grounded context on AI tokenomics from the Tokenomics Foundation's CC BY pages. It covers the Five-Layer Stack, Big-T notation, prompt-caching mechanics and the two official cache metrics, consumption levers, personas, value classification, and the FOCUS 1.5 AI tracker. It is built on the same crawler → markdown-canonical artifact → stdio server pipeline as the framework and FOCUS servers. It links to them through stated cross-links: a quote from the Foundation page that names a FinOps capability or a FOCUS column, checked by tests against the other two artifacts. The decision with the most consequence: this repo is public, and your cert-prep curriculum is private (its site is passcode-gated). So the "labeled extras" layer is a local overlay: it is imported from your checkout at runtime behind the experimental flag, and it never lands in data/ or the npm tarball.

Problem & outcome

Our two servers answer what FinOps says and which billing column holds it. Neither can answer "why does our agent cost 34× what the prototype did?" or "is our prompt cache paying for itself?". The Tokenomics Foundation publishes that vocabulary: T(n·k·a), the five layers, cache hit rate, and cache cost efficiency. It publishes it as bespoke HTML, in Working Draft or Release Candidate status, and the pages change weekly (the cache explainer went through four revisions in September).

When this ships, an agent can:

  • Classify a workload's Big-T class and find the levers that change the class or reduce the constant.
  • Compute Cache Hit Rate and Cache Cost Efficiency from its own token counts using the official formulas.
  • Look up per-provider cache pricing behavior, as dated in the source.
  • Hop to the FinOps capability, the FOCUS column (or the FOCUS 1.5 draft item) the Foundation itself names.

Every answer carries the source document's status, so an agent never presents a Working Draft as a standard.

How it works

Why HTML and not the REST API

Probing showed the WordPress REST API cannot supply page bodies:

  • Project pages arrive as one Custom HTML block with inline script.
  • Theme-template pages return empty content.
  • te_page (Big-T) and asset have no content field at all.
  • The site's own search-data endpoint truncates at 6,000 characters.

So REST is used for discovery and modified dates, and bodies come from the rendered HTML. The pages share one structure, main#primary section.te-section[id], and docs pages use h2 headings. Pages that exist on the site but are not in the registry are listed in manifest.unregistered. When the Optimization Playbook's other layer companions ship, a refresh surfaces them instead of silently ignoring them.

Official vs. unofficial separation (same invariant as the framework server)
  • content/ holds only parsed Foundation text. Formulas are verbatim, and every record carries status.
  • derived/crosslinks.json is official only because each link carries an evidence quote found verbatim in the composed document. A test enforces this.
  • derived/crosswalk.json is official:false, carries a rationale, and is only served under FINOPS_MCP_EXPERIMENTAL=1.
  • The curriculum overlay is official:false, labeled "cert-prep curriculum (unofficial)", loaded only with the flag and TOKENOMICS_MCP_CURRICULUM. Module-original formulas (TK-202 multipliers, TK-205 break-even, TK-305 PVM, TK-303 hit-rate working formula) are tagged module_method.
Failure modes & edge cases
  • A page is redesigned. A parser can fall back to markdown-only for one document; the per-document ingest report records it in parse_warnings. A pinned-count mismatch is a hard error (--soft-counts overrides), so a silent loss of entities fails the refresh.
  • A formula changes between RC revisions. The changelog diff surfaces it. The metrics test compares the artifact formula with the fixture text, so changing the fixture is a deliberate act.
  • Injection text in pages. scanForInjection runs over every composed document, which the FOCUS crawler skipped.
  • Cross-link target renamed upstream. The test fails because it cross-reads data/framework and data/focus. At runtime the link is only a URI, so nothing breaks.
  • calculate_cache_metrics is given nonsense. Negative values or a zero denominator return a tool error, never NaN. Prices are optional; without them, only Cache Hit Rate is computed.

Reference metrics (the "KPI" analog)

These are verbatim from the cache explainer (Release Candidate 1, 2026-09-22):

Cache hit rate = cache read / (cache read + cache write + uncached input) Cache cost efficiency = 1 − actual prompt cost / uncached equivalent cost uncached equivalent cost = (cache read + cache write + uncached input) × base input price

The page's own targets are that hit rate should "climb toward your workload's ceiling" and that cache cost efficiency should be "clearly above zero" (zero is break-even). The other metrics are:

  • net benefit: gross delta × volume − outputs that missed the floor − cost created − harm from misses.
  • risk expected loss: incidents per period × cost per incident.
  • cost per token: hardware cost ÷ tokens produced.
  • AI unit economics: TCA as the numerator over realized value. It is stated in prose and marked "proposed".
