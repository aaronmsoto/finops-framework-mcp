Feature design pipeline

approved  ·  2026-07-13  ·  spec: .agents/specs/design-pipeline.md  ·  roadmap: .agents/roadmap.md

Summary. A defined path from "owner wants a feature" to "loop builds it": intent lands in .agents/roadmap.md, the /design-feature skill produces a rich, self-contained HTML design doc here plus a markdown spec (the machine contract), the owner reviews the design privately (./scripts/agentic serve) — that review is the human checkpoint — and only then does /plan-feature decompose the spec into tasks. Key rule: markdown for machine contracts, HTML for human design surfaces.

Problem & outcome

The template had execution covered (specs → tasks → loop) but nothing upstream: no roadmap tier for product intent, and no home for architecture and interface designs richer than a one-page spec. Prior-art harnesses used a bare GOALS.md backlog and never solved design communication. Outcome: every artifact in the feature lifecycle has a defined home, format, and consumer, and design review happens on a rendered document without any public hosting.

Scope

InOut (non-goals)
Roadmap file; design-doc tier + template; design new/check/publish and serve harness commands; designs quality gate; /design-feature skill; contract updates. Public hosting of any kind; converting machine-facing markdown (specs, memory, prompts, AGENTS.md) to HTML; WYSIWYG tooling; GitHub Pages workflows.

How it works

Privacy model (why this renders nowhere public)

Design docs are single self-contained files: all CSS/JS/SVG inline, and the designs gate fails any external src/href/url() resource or network call in inline script — so opening a design generates zero network traffic. Viewing is via file://, any IDE preview, or agentic serve, which binds strictly to 127.0.0.1. A designs.publishCommand config hook lets an owner push a file to their own internal renderer; nothing publishes by default.

Design doc vs. spec — who reads what

The HTML design is owner-facing rationale (alternatives, diagrams, mockups) and is not loaded into loop prompts. The markdown spec carries the acceptance criteria the loop and verifier enforce. Agents may read a design when a task references it, but the spec is the contract — if they disagree, the spec wins and the design gets updated.

CLI surface

$ ./scripts/agentic design new dark-mode --title "Dark mode"
created docs/designs/dark-mode.html and .agents/specs/dark-mode.md

$ ./scripts/agentic design check          # runs in the fast gate tier
$ ./scripts/agentic serve                 # http://127.0.0.1:4177/ (localhost only)
$ ./scripts/agentic design publish dark-mode   # optional: designs.publishCommand hook

Skill surface

/design-feature — researches the codebase, scaffolds via design new, fills the design + spec, updates the roadmap entry to designing, runs gates, and stops for the owner checkpoint. Existing /plan-feature takes over after approval.

Alternatives considered

OptionVerdict
Convert all docs/ to HTML Rejected: GitHub renders .html as raw source, machine-facing docs pay token overhead for zero layout benefit, and work orgs (GitHub Enterprise) often can't enable Pages. HTML is reserved for the design tier where layout genuinely matters.
GitHub Pages for rendering Rejected as default: private, access-controlled Pages exists only on Enterprise Cloud; on personal private repos Pages is public-or-nothing, violating the no-public-content constraint.
Mermaid diagrams in markdown specs Insufficient alone: fine for small flowcharts, but no layout control, no tabs/mockups, and nothing for interface design. Still usable inside specs where it fits.
GOALS.md-style single backlog file Kept the good part (a lightweight intent file → roadmap.md) and fixed the gap: designs get a real tier instead of living nowhere.
