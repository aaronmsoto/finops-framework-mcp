# T-040 — Add CORS support to the Worker; fix deploy doc and demo hint

Gate 4 finding C4-community-1 (BLOCKER): `src/workers/app.ts` never
answered an OPTIONS preflight and never emitted `Access-Control-Allow-
Origin`, so no browser page — including the T-038 demo, whose whole
purpose is running in a browser against the deployed Worker — could ever
read a cross-origin response, no matter how `ALLOWED_ORIGINS` was set.

## Change

`src/workers/app.ts`'s `createFetchHandler`:

- The existing Origin-allowlist check (absent Origin always allowed;
  present-but-unlisted → 403 before any server work) now runs before CORS
  handling too, so by the time CORS logic runs, `origin` is either `null`
  or already allowlisted.
- New: `request.method === "OPTIONS"` short-circuits straight to a `204`
  reply carrying `Access-Control-Allow-Methods: POST, GET, DELETE, OPTIONS`
  and `Access-Control-Allow-Headers: Content-Type, Accept, Mcp-Session-Id,
  MCP-Protocol-Version`, plus `Access-Control-Allow-Origin` echoing the
  Origin when one was sent. Previously OPTIONS fell through to the SDK
  transport, which 405'd it (confirmed live pre-fix: `PREFLIGHT status:
  405`).
- Every non-preflight response (both routes, plus the 404 fallback) now
  gets `Access-Control-Allow-Origin` set to the request's Origin whenever
  one was sent (it's already passed the allowlist gate above).

## Tests

`src/workers/app.test.ts` gained:
- `Origin allowlist`: two new cases — ACAO present on an allowed-Origin
  POST, ACAO absent when no Origin header is sent.
- New `describe("CORS preflight")`: allowed-Origin OPTIONS on both
  `/mcp/framework` and `/mcp/focus` → 204 + all three CORS headers;
  unlisted-Origin OPTIONS → 403, no ACAO (same allowlist gate as any other
  method — no separate "reject the preflight" logic needed).

## Docs / demo hint

- `docs/deploy-worker.md` §2 (Origin allowlist) now says explicitly that
  `ALLOWED_ORIGINS` is *also* what drives CORS — a browser gets the same
  JSON-RPC response over the wire either way, but silently discards it
  client-side without a matching ACAO header. Previously the doc implied
  the allowlist was purely a server-side accept/reject gate, which is what
  led the demo's error hint to misdiagnose the CORS failure the same way.
- `demo/client.js`'s catch-block hint no longer says "Is ... its Origin
  allowlist configured" as if that's a separate on/off switch; it now
  names `ALLOWED_ORIGINS` as the single setting behind both the accept
  gate and the CORS headers, points at the doc, and notes the failure
  could also be a plain network error.

## Evidence

`./scripts/agentic gates --tier all`: format/lint/typecheck/test (364
tests passed, up from 359 pre-T-039/T-040)/designs/integrity/memory/build
all green; coverage/e2e optional-skip as before. `app.ts` itself shows
100% statement coverage in the run.

Live probe (scratch `node` script, `dist/workers/app.js` +
`createFetchHandler({ allowedOrigins: ["https://demo.pages.dev"] })`,
deleted after use — not committed):
- `OPTIONS /mcp/focus` with `Origin: https://demo.pages.dev` +
  `Access-Control-Request-Method: POST` → `204`, headers include
  `access-control-allow-origin: https://demo.pages.dev`,
  `access-control-allow-methods: POST, GET, DELETE, OPTIONS`,
  `access-control-allow-headers: Content-Type, Accept, Mcp-Session-Id,
  MCP-Protocol-Version`.
- `POST /mcp/focus` (tools/list) with the same allowed Origin → `200`,
  `Access-Control-Allow-Origin: https://demo.pages.dev`.
- `OPTIONS /mcp/focus` with an unlisted Origin → `403`, no ACAO header —
  matches the pre-existing allowlist-reject behavior, no new preflight-
  specific bypass.

This directly reverses the gate's pre-fix reproduction (`PREFLIGHT status:
405`, `POST Access-Control-Allow-Origin: null`).
