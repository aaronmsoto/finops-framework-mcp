# Approvals: the policy system

Human approval points in this template are **compiled, not documented**. You declare policy once in `approvals.yaml` — which actions need a human, which paths are protected, how hard the loop may run — and `./scripts/agentic approvals compile` regenerates every enforcement surface: Claude Code permission rules, the guarded Copilot wrapper, CODEOWNERS, and the GitHub branch ruleset. `approvals check` in CI guarantees the surfaces never drift from the policy. This doc walks the schema, explains how each surface enforces, and covers how policy changes are themselves gated.

## The schema: `approvals.yaml`

This is the one policy file the owner edits. Never edit the generated surfaces by hand.

```yaml
version: 1
owner: "@your-github-handle"
approvals:
  merge_to_main: human        # human | auto
  deploy_production: human    # human | auto
  release: human              # human | auto
  force_push: never           # never | human
protected_paths:
  - ".agentic/harness/tests/**"
  - ".github/workflows/**"
  - "approvals.yaml"
  - "agentic.config.json"
  - ".claude/settings.json"
commands:
  ask:
    - "Bash(git push origin main*)"
    - "Bash(gh pr merge*)"
  deny:
    - "Bash(git push --force*)"
loop:
  max_iterations: 10
  max_wall_minutes: 120
  max_consecutive_failures: 3
```

Key by key:

- **`version`** — schema version, currently `1`.
- **`owner`** — your GitHub handle; every generated CODEOWNERS line points at it.
- **`approvals`** — the named approval points. `human` compiles into enforcement (ask rules, CODEOWNERS, ruleset review requirements); `auto` removes the human requirement for that point. `force_push` accepts `never` (compiles to hard deny rules) or `human`.
- **`protected_paths`** — glob patterns that get a CODEOWNERS entry *and* in-session edit protection via the PreToolUse hook. The defaults protect exactly the things an agent could use to lower its own bar: tests, workflows, the policy file, the gate config, and the Claude settings.
- **`commands.ask`** — command patterns compiled verbatim into `permissions.ask` in `.claude/settings.json`: the agent must stop and get interactive confirmation. Note the shipped patterns gate pushes *to main* and merges — feature-branch pushes and PR creation stay free, because the human gate is the merge, not the proposal.
- **`commands.deny`** — compiled into `permissions.deny` *and* into `--deny-tool` flags in `scripts/copilot.sh`: never allowed, no prompt.
- **`loop`** — the hard caps the harness enforces. Defaults (used even if the section is absent): 10 iterations, 120 wall-clock minutes, 3 consecutive failures. CLI flags may only lower these; raising one means editing this file, which is itself a protected path.

## What `approvals compile` generates

Each generated file carries a `GENERATED by agentic approvals compile — edit approvals.yaml instead` header where the format allows.

### 1. `.claude/settings.json` — Claude Code permissions

The compiler **owns the `permissions.ask` and `permissions.deny` arrays entirely** (put personal additions in `settings.local.json`, which is not compiler-managed) and merges non-destructively with the rest of the file, so hooks survive recompiles. `force_push: never` becomes deny entries; each `human` approval point becomes ask entries; `commands.ask`/`commands.deny` are carried over verbatim.

How it enforces: this is the load-bearing verified fact from the research — **explicit `ask` rules survive `bypassPermissions` mode** ([research-synthesis.md](research/research-synthesis.md), "Human approval gates"). Even an agent launched in full-yolo mode stops at `git push origin main` or `gh pr merge` and asks a human. Deny and ask rules also apply before workspace trust is granted, so a freshly cloned repo is protected from the first session.

### 2. `scripts/copilot.sh` — the guarded Copilot wrapper

Copilot CLI has **no repo-committed permissions file** — there is nothing like `.claude/settings.json` to generate into. The wrapper is therefore the repo-committed policy carrier: an executable script that runs `exec copilot "$@"` with the compiled `--deny-tool` flags appended.

How it enforces: Copilot's `--deny-tool` beats `--allow-tool` and even `--allow-all`, so the denies hold in YOLO mode too — as long as sessions go through the wrapper. That is why [AGENTS.md](../../AGENTS.md) and the loop's copilot runner both use `scripts/copilot.sh`, never bare `copilot`. The wrapper is convention-plus-tooling, not an inescapable jail: a human typing `copilot` directly bypasses it, which is acceptable because humans are not the threat model.

### 3. `.github/CODEOWNERS` — human review on the paths that matter

`merge_to_main: human` produces `* @owner`; each `protected_paths` entry gets its own line.

How it enforces: once the ruleset (below) requires review, GitHub will not let a PR touching those paths merge without the owner's approval. An agent cannot approve or merge its own PR, so this is the surface that makes "a human merges" structural rather than instructional — including for PRs that modify the policy or the tests.

### 4. `.github/rulesets/main-branch.json` — the branch ruleset

An importable GitHub ruleset requiring: pull requests to the default branch, 1 human review, the `gates-fast` status check (and `gates-full` when a merge queue is configured), with force pushes and branch deletion blocked. The targeted branch is `branching.default_branch` (default `main`); the file keeps the stable name `main-branch.json` regardless. If you set a non-`main` default branch, also hand-edit `.github/workflows/ci.yml` and `release-pr.yml` — they embed the branch name literally and are owner-owned (the compiler never generates workflows).

How it enforces: server-side, on GitHub — the one surface no local configuration can route around. Applying it is a one-time manual or API step ([getting-started.md](getting-started.md#wire-up-github)); the JSON in the repo is the versioned, reviewable source.

Beyond the four compiled surfaces, GitHub Environments guard deployment: a `production` Environment with required reviewers withholds its secrets until a human approves the deployment run, keeping production credentials out of agent-triggered workflows entirely. Environments are configured in the GitHub UI/API, not compiled.

## `approvals check`: the drift gate

`./scripts/agentic approvals check` recompiles everything to a temp location and diffs against the committed surfaces; any difference is a nonzero exit. CI runs it in the `gates-fast` job, which means:

- A hand-edit to a generated file fails CI until reverted or made in `approvals.yaml`.
- An edit to `approvals.yaml` without rerunning `compile` fails CI until the surfaces are regenerated.

Policy and enforcement therefore cannot diverge on main.

## Changing the policy

The system gates changes to itself:

1. Edit `approvals.yaml` (and nothing generated).
2. Run `./scripts/agentic approvals compile`; commit the yaml and all regenerated surfaces together.
3. Open a PR. Because `approvals.yaml`, `.claude/settings.json`, and `.github/workflows/**` are protected paths, CODEOWNERS requests the owner's review automatically.
4. The owner reviews the policy diff *and* the generated diffs (they should correspond exactly — `approvals check` verifies) and merges.

An agent can propose a policy change through this exact flow; it cannot land one alone.

### In-session protection: the protect-policy hook

A PreToolUse hook (`scripts/hooks/`, wired in `.claude/settings.json`) blocks agent edits to protected paths before the permission system even evaluates them. When a hook blocks an edit, the right response — for the agent — is to stop and say so, not to work around it.

For legitimate supervised edits (you are sitting there, directing the agent to update the policy), the override marker is `.agents/.cache/policy-edit-ok`: create the file, let the supervised edit happen, and it is gone with the gitignored cache. The marker lives in the uncommitted cache directory deliberately — an agent cannot commit itself an exemption, and the override never travels to CI, where `approvals check` and CODEOWNERS still apply.

## Limitations

Honest edges of the system, all rooted in platform constraints:

- **Copilot has no repo-committed permissions file.** Policy reaches Copilot only through the wrapper (and the shared git-hooks/CI/ruleset layer). Bare `copilot` invocations carry no repo policy.
- **Ruleset JSON import excludes bypass lists.** After importing `.github/rulesets/main-branch.json`, review the ruleset's bypass configuration in the GitHub UI — an unnoticed bypass actor undermines the whole surface.
- **Required reviewers on Environments may need a paid plan for private repos.** If your private repo's plan does not support them, deploy protection falls back to `commands.ask` rules and the fact that deploy workflows only run from main (which is itself merge-gated).
- **Ask rules are interactive.** In a fully headless run there is no human to answer an ask prompt, so the guarded action simply does not happen — which is the correct failure mode, but worth knowing when a loop log shows a stalled push.
